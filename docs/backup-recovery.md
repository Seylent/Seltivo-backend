# Резервування та відновлення SQLite

Ця процедура стосується локальної SQLite БД Node.js бекенду. Команди виконуються з каталогу `Seltivo backend` після `npm ci` і `npm run build`. Для Cloudflare Durable Object потрібна окрема процедура експорту й відновлення.

## Робочий режим для затвердження

- Щоденна копія о 03:00 за часом `Europe/Kyiv`; у назві файлу використовуйте UTC, щоб перехід на літній час не створив однакових назв. Це дає втрату щонайбільше приблизно 24 годин записів при аварії між копіями. Якщо така втрата неприйнятна, графік треба змінити до запуску.
- Зберігайте 30 останніх днів щоденних копій і окрему копію перед кожним розгортанням, яке змінює схему. Строк 30 днів є пропозицією до затвердження разом із політикою видалення акаунтів.
- Зберігайте копії поза live томом, із доступом лише для операторів відновлення та шифруванням сховища. Перевіряйте успішність завдання щодня. Після зміни схеми й щомісяця проводьте відновлення в ізольованому staging.
- Команда `backup` не видаляє старі файли. Налаштуйте ротацію у планувальнику хоста лише після затвердження строку зберігання. Не видаляйте останню перевірену копію.

## Створення копії

1. Встановіть `SELTIVO_DB_PATH` на шлях до наявної робочої БД. Не запускайте нову версію сервера перед передрелізною копією: сервер застосовує міграції при відкритті БД.
2. Запустіть `npm run backup -- "D:\backups\seltivo-20261114T010000Z.db"` із новою унікальною назвою. Команда читає вихідну БД без міграції, робить SQLite online backup і перевіряє `integrity_check` та `foreign_key_check` у копії. Вона не перезаписує наявний файл.
3. Зафіксуйте час, шлях, розмір, результат перевірки та версію застосунку в операторському журналі без персональних даних. Перенесіть копію в захищене місце поза live томом.

## Репетиція відновлення в staging

1. Обмежте доступ до staging так само, як до production: копія містить реальні акаунти, заявки й повідомлення. Вимкніть вихідну пошту та інші зовнішні інтеграції. Зупиніть staging бекенд. Збережіть його поточну БД окремо, якщо вона потрібна.
2. Скопіюйте вибраний `.db` у новий шлях на локальному диску staging. Не копіюйте активний production `.db` напряму; джерелом має бути перевірений файл online backup.
3. Виконайте `npm run backup:verify -- "D:\staging\restored.db"`. Це перевіряє цілісність і зовнішні ключі без запису в БД. Зафіксуйте показану версію схеми. Якщо вона старіша за версію застосунку, збережіть цей файл і відкривайте окрему робочу копію — запуск сервера оновить її міграціями.
4. Встановіть `SELTIVO_DB_PATH` на робочу копію, `SELTIVO_PUBLIC_ORIGIN` на staging origin і запустіть бекенд. Ще раз виконайте `backup:verify` для цієї БД. Перевірте `GET /api/v1/health` через той самий проксі, яким користується Next.
5. Увійдіть контрольованим акаунтом, відкрийте наявну заявку та її повідомлення. Створіть нову тестову заявку, надішліть повідомлення, увійдіть адміністратором і дайте відповідь. Перевірте, що клієнт бачить відповідь. Якщо в копії немає контрольованого акаунта, створіть його лише в staging після відновлення.
6. Запишіть результат, тривалість до робочого стану й причину будь-якої невдачі. Не повертайте staging з production даними у публічний доступ. Видаліть тимчасову копію за погодженим строком доступу до тестових даних.

Локальний автоматичний тест `tests/backup.test.ts` повторює кроки цілісності, входу, заявки й чату на ізольованій відновленій БД. Він не замінює перевірку staging, проксі та мережі.

## Видалення акаунта й даних у копіях

Автоматичного видалення акаунта зараз немає. Поки не затверджені підстави й строки зберігання заявок, діалогів та аудиту, не обіцяйте повне видалення через інтерфейс. Узгодьте, які записи видаляються або знеособлюються в активній БД, хто підтверджує запит і як фіксується факт виконання.

Вже створені копії не слід переписувати вибірково: це може зруйнувати можливість відновлення. Запропонований режим — видаляти їх після 30 днів і не відновлювати видалений акаунт із давньої копії. Перед поверненням відновленої БД у production оператор має повторно застосувати журнал виконаних запитів на видалення, зроблених після часу копії, та перевірити результат. Поки немає затвердженої політики й такого журналу, повне видалення акаунта лишається невиконаним пунктом P0.
