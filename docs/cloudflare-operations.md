# Cloudflare Worker: дані та реагування

Production використовує SQLite-backed Durable Object `SeltivoData` з ім'ям `primary`. Локальні команди `npm run backup` і `backup:verify` стосуються тільки Node/SQLite і **не створюють копії production Worker**.

## Схема та реліз

- Код зберігає версію Worker БД у таблиці `schema_migrations`. `PRAGMA user_version` у Cloudflare Durable Object не підтримується. Міграції застосовуються послідовно в одній синхронній транзакції перед обробкою запитів. Невідома новіша версія або несумісна стара схема зупиняє об'єкт.
- Перед релізом, що змінює схему, зафіксуйте час, поточну версію коду, поточний [PITR bookmark](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#pitr-point-in-time-recovery-api) і результат `GET /api/v1/admin/diagnostics` операторським акаунтом. Нову версію спочатку перевірте на окремому staging об'єкті зі знеособленими даними. Staging зараз відсутній, тому цей release gate ще не виконаний.
- Після релізу перевірте `GET /api/v1/health`, адміністраторську діагностику, вхід, заявку, діалог і повтор клієнтського запиту. Для відкату коду з версією схеми, новішою за код, потрібна сумісна версія Worker; старий код навмисно відмовиться відкрити БД.

## Відновлення й видалення

Узгоджений режим — щоденна незалежна копія з 30-денним зберіганням. Зараз окремий експорт/сховище копій **не налаштовано**. Cloudflare надає [PITR за останні 30 днів](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#pitr-point-in-time-recovery-api), але його bookmark не є незалежним файлом копії. API `onNextSessionRestoreBookmark` відновлює **цей самий Durable Object** після рестарту; локальний `wrangler dev` не підтримує PITR. Не застосовуйте пробне відновлення до production.

До production-критерію P0 лишаються окреме сховище/процедура щоденних копій та ізольований staging для пробного відновлення. Після створення staging перевіряйте `quick_check` і зовнішні ключі через `/api/v1/admin/diagnostics`, а далі вхід, заявку, відповідь адміністратора й історію. Durable Object відхиляє `PRAGMA integrity_check` з `SQLITE_AUTH`, тому цей endpoint не може виконати саме цю повну перевірку. Фіксуйте час від початку відновлення до успішної перевірки; це буде фактична тривалість відновлення.

Узгоджено видаляти клієнтський акаунт разом із конфігураціями, заявками й чатом з активної БД; дані у вже створених копіях можуть залишатися до завершення їхнього 30-денного строку. Окремий Durable Object `DeletionLedger` у тому самому Worker зберігає ID підтверджених видалень і час. Після PITR відновлюйте **лише** основний об'єкт `SeltivoData`; його запуск повторно видалить ці акаунти за журналом. Видалення в API вимагає поточного пароля й очищує сесію. Журнал не містить email або текстів, але ID поки зберігаються без строку автоматичного видалення, щоб старе відновлення не повернуло дані.

Функція **вимкнена за замовчуванням**. Вмикайте `SELTIVO_ACCOUNT_DELETION_ENABLED=1` лише після перевірки restore на окремому staging Durable Object і підтвердження незалежних копій. Окремий Durable Object захищає від PITR відкату основного об'єкта, але не замінює незалежну копію чи захист від втрати всього Cloudflare акаунта. `DELETE /configurations/:id` лише приховує збережений варіант і не стирає знімок у заявці.

## Пошта

У Worker налаштуйте `BREVO_API_KEY` і `BREVO_SENDER_EMAIL` через Wrangler secrets. Повідомлення чату зберігається перед викликом Brevo. Кожен лист чату має запис у `email_notifications` зі станом `pending`, `sending`, `sent` або `failed`; помилка не стирає повідомлення. Адміністратор бачить недоставлені листи на `/admin/email-notifications` і може повторити відправлення. Повтор використовує наявний `message_id`; сам лист може бути доставлений двічі, якщо провайдер прийняв попередню спробу, а відповідь загубилась. Секрети й текст листа не записуються в журнал помилок.

Для листа відновлення пароля зберігається лише хеш токена; невдалу доставку цього листа не можна безпечно повторити з адмінки. Користувач може запросити нове посилання. Команда має перевірити реальну доставку після налаштування Brevo.

## Метрики й короткі дії при збої

У `wrangler.jsonc` увімкнені Workers Logs. Кожен запит Worker записує `event=api_request`, `requestId`, метод, HTTP статус, тривалість у мс і розмір SQLite у байтах. Невдача листа записує `event=email_delivery_failed` і код без адреси, токена чи тексту. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) та [Workers metrics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/) доступні в Cloudflare dashboard. Пороги нижче — початкові; уточніть їх після тижня фактичних вимірів.

| Сигнал | Початковий поріг | Дія |
| --- | --- | --- |
| HTTP 5xx | понад 1% за 10 хв при щонайменше 100 запитах | Зіставити `requestId` з логом, перевірити останній реліз, `/health` і `/admin/diagnostics`; зупинити реліз при рості помилок. |
| Час API | p95 понад 2 с за 15 хв | Перевірити, які операції йдуть із затримкою, стан Brevo та розмір БД; не змінювати індекси без `EXPLAIN QUERY PLAN`. |
| Пошта | хоча б один `failed` понад 15 хв | Відкрити адмінку пошти, перевірити Brevo/секрети й повторити відправлення після усунення причини. |
| Розмір БД | понад 70% ліміту тарифу або ріст понад 20% за тиждень | Перевірити розмір JSON конфігурацій/заявок і план зберігання; не видаляти дані без процедури. |
| Копії/restore | немає незалежної щоденної копії або невдалий staging restore | Не оголошувати P0 готовим; зафіксувати інцидент і причину. Тривалість backup стане вимірюваною після реалізації експорту. |

У Cloudflare dashboard ще треба налаштувати сповіщення за цими порогами та призначити чергового. Самі пороги в документі не створюють автоматичних alerts.
