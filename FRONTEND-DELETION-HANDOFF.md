# Передача фронту: self-service видалення акаунта

Статус: бекенд готовий і увімкнений у prod/staging (`SELTIVO_ACCOUNT_DELETION_ENABLED=1`). У репо фронту на `a8aaf74` UI вже є (`src/app/(platform)/account/ProfileSettings.tsx:48-61`, прапорець із `account/page.tsx:272`), тож передається **контракт і чеклист доробки**, не реалізація з нуля.

## Контракт

**Доступність:** `GET /api/v1/me` повертає `accountDeletionAvailable: true` тільки для `role: "customer"` за наявності бекенд-компонента видалення й увімкненого прапорця. Якщо `false` — кнопку ховаємо/дисаблемо.

**Запит:**
```
DELETE /api/v1/me
Content-Type: application/json
Cookie: seltivo_session=<HttpOnly>          // ставиться браузером
Body: { "password": "<поточний пароль>" }   // 1..200 символів, strict — лише password
```
Викликати **тільки через власний Next-проксі** `/api/v1/*` (`accountApi("/me", …)`), не напряму до Worker: бекенд вимагає `Origin` рівно `SELTIVO_PUBLIC_ORIGIN`.

**Успіх:** `204 No Content`, у відповіді `Set-Cookie: seltivo_session=; Max-Age=0`. Тіла немає — клієнт має не намагатися парсити JSON (`account-api.ts:106` уже обробляє 204).

**Помилки:**
| Статус | Причина | Що показати |
| --- | --- | --- |
| 401 | Невірний пароль | «Невірний поточний пароль» |
| 403 | Непідтверджений email або роль не customer | «Підтвердьте email» / недоступно |
| 422 | Невалідне тіло | загальна помилка форми |
| 429 | Ліміт 10 спроб/хв за IP | «Забагато спроб, спробуйте пізніше» |
| 503 | Функцію вимкнено / немає журналу видалень | «Тимчасово недоступне» |
| 500 | Помилка журналу видалень (репліка не гарантована) | «Спробуйте пізніше», не вважати видаленням |

**Що видаляється на бекенді:** користувач, конфігурації, заявки, діалоги, повідомлення, сповіщення, сесії, токени й аудит-записи. Старий токен після цього повертає 401. Копії у бекапах/R2 мають вік до 30 днів, а журнал видалень не дає PITR-відкату воскресити дані — саме це вже написано в UI (`ProfileSettings.tsx:105`), текст лишати.

## Чеклист доробки на фронті

1. **Чистити клієнтський стан після 204** (зараз робиться тільки `router.replace("/")` + `router.refresh()`):
   - `clearAccountCache()` — вже викликається на будь-якій мутації в `account-api.ts:38`;
   - `clearPendingSignIn()` (`src/lib/pending-signin.ts:42`) — інакше чужий email лишиться в localStorage/sessionStorage і підставиться в `/verify-email`;
   - усі ключі `seltivo-request-*` у sessionStorage через `clearSubmissionId` (`src/lib/submission-id.ts:27`) — інакше retry-ID від видаленого акаунта переживе вихід;
   - чернетки Studio в IndexedDB (`atelier-configurator`, `src/studio/lib/configDraft.ts`) — продукт має вирішити: це browser-local стан чи приватні дані; за видалення акаунта доцільно очистити.
2. **Повторний вхід у тій самій вкладці**: після 204 не показувати кешованого `/me`; перевірити, що `CurrentUserProvider` не підставить старого користувача з `meCache` (TTL 15 с) між `replace` і `refresh`.
3. **Не робити live-перевірок на проді.** Smoke-сценарій — лише staging із dummy-акаунтом; бекенд має `scripts/cloudflare-deletion-smoke.mjs`, який відмовляється від prod-origin. Frontend-тест (Playwright): зареєструвати dummy, видалити, перевірити 401 на `/api/v1/me` і відсутність кнопки після редиректу.
4. **Формулювання підтвердження**: чекбокс «не можна скасувати» вже є; лишати явне попередження про 30 днів у копіях.
